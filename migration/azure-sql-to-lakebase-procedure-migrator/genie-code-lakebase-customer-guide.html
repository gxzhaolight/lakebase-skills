CUSTOMER ENABLEMENT / LAKEBASE

Move one stored procedure at a time—from Azure SQL to Lakebase.

Use a Genie Code skill to make the migration repeatable: analyze first, convert with an explicit contract, then validate in a safe development branch.

Simple rule: generated code is a draft until the customer reviews the diff and verifies behavior against representative test data.

03 / TEACH

A simple customer walkthrough

Start with one representative procedure and its dependent tables/views—not the whole estate.

1

Prepare the inputs

Bring the T-SQL procedure, dependent DDL, caller contract, sample inputs, and expected outputs.

2

Use a safe target

Choose a development Lakebase project or branch. Do not run generated code against production.

3

Analyze first

Ask Genie Code to classify the logic as a Lakebase function, procedure, trigger, application workflow, or Lakeflow workflow.

4

Review before approval

Read the dependencies, T-SQL-only behavior, target contract, security risks, transaction risks, and blockers.

5

Convert and validate

Generate the Lakebase SQL, tests, migration notes, and report. Compare results, errors, rollback behavior, concurrency, and performance.

Prompt A — analyze first
Analyze the Azure SQL stored procedure at <SOURCE_PATH> for migration to Lakebase PostgreSQL.
Do not modify source files or run anything yet.
Inspect dependencies and classify the target as a Lakebase function, procedure, trigger,
application workflow, or Lakeflow workflow. Document the target contract, T-SQL-only
behavior, security and transaction risks, blockers, and validation plan. Wait for approval.
Prompt B — convert after approval
Convert the approved procedure to Lakebase PostgreSQL for project <PROJECT>,
branch <DEV_BRANCH>, database <DATABASE>, and schema <SCHEMA>.
Preserve the caller contract where safe. Generate the .lakebase.sql file, migration
notes, tests, and migration_report.md. Validate only in this non-production target.
Show diffs and mark uncertain behavior NEEDS_REVIEW.
04 / VALIDATE

Definition of done

Do not call the migration production-ready until the customer has evidence, not just a successful parse.

Source definitions remain unchanged.
Every dependency and target mapping is recorded.
Function/procedure/trigger choice is justified.
Parameters and return contracts are explicit.
Errors, rollback, retries, and idempotency are tested.
Identity, sequences, timestamps, NULLs, and boundaries are tested.
Security roles, grants, and row-level restrictions are reviewed.
Concurrency and critical-path performance are checked.
The target ran only in a non-production Lakebase environment.
The report separates verified behavior from assumptions.
Recommended customer language“This procedure is ready for the next migration stage” is safer than “this procedure is production-ready” until functional, security, concurrency, reconciliation, and performance checks have passed.
